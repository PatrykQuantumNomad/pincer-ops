**Create scripts/lib/sealed-secrets.sh:**
A helper library sourced by bootstrap.sh containing sealing key backup/restore functions. Follow the common.sh pattern (sourced, not executed directly).

Constants:
- `SEALED_SECRETS_BACKUP_DIR="${SEALED_SECRETS_BACKUP_DIR:-${HOME}/.pincer}"` (configurable via env var)
- `SEALED_SECRETS_BACKUP_FILE="${SEALED_SECRETS_BACKUP_DIR}/sealed-secrets-key.yaml"`
- `SEALED_SECRETS_NAMESPACE="kube-system"` (upstream default, avoids kubeseal CLI friction)

Functions:
- `backup_sealing_key()`: Creates backup dir if needed, runs `kubectl get secret -n "${SEALED_SECRETS_NAMESPACE}" -l sealedsecrets.bitnami.com/sealed-secrets-key -o yaml > "${SEALED_SECRETS_BACKUP_FILE}"`, logs success. Returns 0 on success, 1 on failure. Uses `log_info` and `log_step` from common.sh.
- `restore_sealing_key()`: Checks if backup file exists. If yes, ensures the namespace exists (kube-system always exists, but check anyway), runs `kubectl apply -f "${SEALED_SECRETS_BACKUP_FILE}"`, logs success, returns 0. If no backup, logs info "No sealing key backup found (first run)", returns 1.
- `restart_sealed_secrets_controller()`: Runs `kubectl rollout restart deployment/sealed-secrets-controller -n "${SEALED_SECRETS_NAMESPACE}"` then `kubectl rollout status deployment/sealed-secrets-controller -n "${SEALED_SECRETS_NAMESPACE}" --timeout=60s`. Used after key restore if controller already started.

**Step 14: Deploy Sealed Secrets**
The flow must be:
1. Try to restore sealing key from backup (BEFORE controller starts -- see research Pitfall 2)
2. Apply the infra-sealed-secrets Application directly (same pattern as Envoy Gateway in Step 12 -- ArgoCD Helm app applied directly)
3. Wait for Sealed Secrets controller: poll for `deployment/sealed-secrets-controller -n kube-system` to exist (same polling pattern as MetalLB in Step 10). If ArgoCD cannot sync (placeholder repoURL), fall back to direct kustomize apply of `infrastructure/sealed-secrets/base`. Use 180s timeout matching MetalLB pattern.
4. `kubectl wait --for=condition=available deployment/sealed-secrets-controller -n kube-system --timeout=120s`
5. If key was restored in step 1, restart the controller to pick up restored keys: `restart_sealed_secrets_controller`
6. Backup sealing key: `backup_sealing_key` (captures current key -- on first run this is the new key, on subsequent runs it updates the backup)
7. Log success

Use a variable `KEY_RESTORED=false` to track whether restore happened (affects step 5).

**Step 15: Deploy cert-manager**
The flow (simpler than Sealed Secrets -- no key lifecycle):
1. Apply the infra-cert-manager Application directly
2. Wait for cert-manager controller: poll for `deployment/cert-manager -n cert-manager` to exist. Same fallback pattern -- if ArgoCD cannot sync, apply `infrastructure/cert-manager/base` directly via kustomize. Use 180s timeout.
3. `kubectl wait --for=condition=available deployment/cert-manager -n cert-manager --timeout=120s`
4. Also wait for cert-manager webhook: `kubectl wait --for=condition=available deployment/cert-manager-webhook -n cert-manager --timeout=120s` (webhook must be ready before Certificates can be issued)
5. Log success

     namespace: default

     secretName: test-cert-tls
