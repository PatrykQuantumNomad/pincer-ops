  <action>
    Create the OpenShell security policy ConfigMap and add it to the existing Kustomize resources list.

    1. **policy-configmap.yaml** (POL-01): Create a new ConfigMap manifest with the complete OpenShell policy schema v1. Follow the research-provided template exactly:

       - `apiVersion: v1`, `kind: ConfigMap`
       - `metadata.name: openshell-sandbox-policy`, `metadata.namespace: openshell`
       - Single data key: `policy.yaml` containing the inline YAML policy
       - Header comment following project convention: "# policy-configmap.yaml -- OpenShell security policy for the openclaw-sandbox."

       The policy YAML must contain these four sections (and ONLY these four -- no seccomp fields):

       **filesystem_policy:**
       - `include_workdir: false` (we explicitly list all paths; no implicit workdir addition)
       - `read_only:` paths: `/usr`, `/lib`, `/lib64`, `/etc`, `/proc`, `/dev/urandom`, `/opt/openshell/bin`
         - `/usr`, `/lib`, `/lib64`: System libraries and Node.js runtime
         - `/etc`: System config (resolv.conf, hosts, SSL certs)
         - `/proc`: Process info (Node.js reads /proc/cpus, /proc/meminfo)
         - `/dev/urandom`: Crypto random (Node.js crypto module)
         - `/opt/openshell/bin`: Supervisor binary (DaemonSet-loaded via hostPath)
       - `read_write:` paths: `/home/node/.openclaw`, `/tmp`, `/home/node/.cache`, `/dev/null`
         - `/home/node/.openclaw`: PVC data directory (OpenClaw's main data store)
         - `/tmp`: Temp files (emptyDir)
         - `/home/node/.cache`: Node.js cache (emptyDir)
         - `/dev/null`: Standard null device

       **landlock:**
       - `compatibility: best_effort` -- v2.1 uses log-only enforcement per user decision. Gracefully degrades on older kernels. Observe violations before switching to hard_requirement.

       **process:**
       - `run_as_user: "1000"` -- matches sandbox pod securityContext.runAsUser
       - `run_as_group: "1000"` -- matches sandbox pod securityContext.runAsGroup
       - Must NOT be root/0 (rejected by supervisor)

       **network_policies:**
       - Single policy entry: `openshell_gateway` for the gateway gRPC endpoint
       - `name: openshell-gateway-grpc`
       - `endpoints:` one entry: `host: openshell.openshell.svc.cluster.local`, `port: 8080`, `enforcement: enforce`
       - `binaries:` one entry: `path: /opt/openshell/bin/openshell-sandbox`
       - This is the tightest viable set because:
         - inference.local resolves via loopback in the supervisor's network namespace (no policy entry needed)
         - LLM provider calls are made by the privacy router outside the sandbox netns (no policy entry needed)
         - DNS is handled by the supervisor's netns resolver config (no policy entry needed)
         - Only the gateway gRPC endpoint needs an explicit policy entry

       Add inline comments to each section explaining the rationale, matching the style from the research Example 1.

    2. **kustomization.yaml** (POL-06): Add `policy-configmap.yaml` to the resources list.
       - Add it AFTER `networkpolicy.yaml` (last entry) to keep the ordering logical: CRD, app config, service, routing, network, policy.
       - Keep ALL existing entries unchanged: `sandbox.yaml`, `configmap.yaml`, `service.yaml`, `httproute.yaml`, `networkpolicy.yaml`.
       - Preserve the existing `apiVersion`, `kind`, and `namespace` fields exactly.

    CRITICAL CONSTRAINTS (from research):
    - Do NOT add any seccomp fields to the policy YAML. The supervisor binary applies its own built-in seccomp profile at sandbox creation time. The policy schema v1 proto has no seccomp field. Adding one will cause `openshell policy set` to fail with a validation error.
    - Do NOT use configMapGenerator. The hash suffix would break the registration Job's volume mount reference in Phase 31. Use a plain ConfigMap resource.
    - Do NOT add inference.local or LLM provider hosts (api.anthropic.com, etc.) to network_policies. The privacy router handles those outside the sandbox netns.
  </action>
