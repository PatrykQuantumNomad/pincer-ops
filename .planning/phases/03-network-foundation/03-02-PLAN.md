  <action>
Run a full cluster teardown and bootstrap cycle to test the complete flow.

**Step 1: Teardown existing cluster (if any)**
```bash
./scripts/teardown.sh
```

**Step 2: Run bootstrap**
```bash
./scripts/bootstrap.sh --verbose
```

Use `--verbose` to see full output for debugging. The bootstrap should:
1. Create the KIND cluster (Steps 1-4)
2. Calculate MetalLB IP range from CIDR (Step 5)
3. Install ArgoCD (Steps 6-8)
4. Apply root-app (Step 9)
5. Wait for MetalLB deployment via ArgoCD (Step 10)
6. Apply MetalLB L2 config (Step 11)

If bootstrap fails at any step, diagnose and fix the issue. Common failure points per research:
- Step 10 timeout: ArgoCD sync may be slow. Check `kubectl get app infra-metallb -n argocd` for sync status. If the Application is not being discovered, check root-app scan path includes bootstrap/.
- Step 10 webhook: If MetalLB webhook is not ready, the wait for deployment/controller should handle this. If it does not, check `kubectl get pods -n metallb-system`.
- Step 11 IPAddressPool rejected: MetalLB webhook must be ready. The wait in Step 10 should prevent this.

**Step 3: Verify MetalLB components**
After bootstrap completes, verify:

```bash
# Verify MetalLB pods are running
kubectl get pods -n metallb-system

# Verify MetalLB ArgoCD Application exists
kubectl get app infra-metallb -n argocd

# Verify IPAddressPool and L2Advertisement exist
kubectl get ipaddresspool -n metallb-system
kubectl get l2advertisement -n metallb-system

# Verify the IP range is from the KIND CIDR (not hardcoded)
kubectl get ipaddresspool kind-pool -n metallb-system -o yaml
```

Expected: controller pod Running, speaker pods Running on all nodes, infra-metallb Application exists, kind-pool IPAddressPool with address range matching X.Y.255.200-X.Y.255.250, kind-l2 L2Advertisement referencing kind-pool.

**Step 4: Test LoadBalancer IP assignment**
Create a test service and verify MetalLB assigns an external IP:

```bash
# Create test deployment and LoadBalancer service
kubectl create deployment nginx-test --image=nginx:1.27 --port=80 -n default
kubectl expose deployment nginx-test --type=LoadBalancer --port=80 -n default

# Wait for external IP assignment (MetalLB should assign within seconds)
kubectl wait --for=jsonpath='{.status.loadBalancer.ingress[0].ip}' \
  service/nginx-test -n default --timeout=30s

# Get the assigned IP and verify it is in the MetalLB range
kubectl get svc nginx-test -n default -o wide
```

The EXTERNAL-IP should be in the X.Y.255.200-250 range (matching the calculated MetalLB pool).

**Step 5: Clean up test resources**
```bash
kubectl delete deployment nginx-test -n default
kubectl delete service nginx-test -n default
```

If ANY step fails, apply Rule 1 (auto-fix) from the deviation handling protocol: diagnose the issue, fix the source file, and retry. Common fixes:
- If infra-metallb Application is not discovered by root-app: verify the file is in bootstrap/ (not infrastructure/)
- If kustomize remote resource fails: ArgoCD repo-server may not be able to reach GitHub. Fall back to downloading the manifest and committing it (see research Open Question 2)
- If MetalLB webhook timing fails: increase the polling timeout or add explicit webhook readiness check
