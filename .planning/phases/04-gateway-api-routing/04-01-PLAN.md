**1. infrastructure/envoy-gateway/base/envoy-proxy-config.yaml** -- EnvoyProxy CRD for KIND/macOS:
```yaml
apiVersion: gateway.envoyproxy.io/v1alpha1
kind: EnvoyProxy
metadata:
  name: kind-proxy-config
  namespace: envoy-gateway-system
spec:
  provider:
    type: Kubernetes
    kubernetes:
      envoyDaemonSet:
        pod:
          nodeSelector:
            ingress-ready: "true"
          tolerations:
            - key: node-role.kubernetes.io/control-plane
              operator: Exists
              effect: NoSchedule
        patch:
          type: StrategicMerge
          value:
            spec:
              template:
                spec:
                  containers:
                    - name: envoy
                      ports:
                        - containerPort: 8080
                          hostPort: 80
                          name: http
                          protocol: TCP
                        - containerPort: 8443
                          hostPort: 443
                          name: https
                          protocol: TCP
      envoyService:
        type: ClusterIP
```
- `envoyDaemonSet` switches from Deployment to DaemonSet mode
- `nodeSelector: { ingress-ready: "true" }` targets KIND control-plane node (labeled in kind-config.yaml)
- Tolerations for control-plane taint -- CRITICAL or pod stays Pending
- containerPort 8080 maps to hostPort 80 (Envoy maps privileged ports to unprivileged internally)
- containerPort 8443 maps to hostPort 443
- `envoyService.type: ClusterIP` -- no LoadBalancer needed since hostPort handles host access
- Add header comment explaining the KIND/macOS networking rationale

**2. infrastructure/envoy-gateway/base/gateway-class.yaml** -- GatewayClass:

**Step 12: Deploy Envoy Gateway controller**
This step handles the Helm-source Application (infra-envoy-gateway). Since it uses an OCI source (docker.io/envoyproxy), it should NOT be affected by the placeholder repoURL. However, ArgoCD needs to discover and process it. Strategy:
- After MetalLB is configured, the root-app should discover infra-envoy-gateway.yaml from bootstrap/
- Wait for the Envoy Gateway controller deployment to exist in envoy-gateway-system namespace
- Use the same polling pattern as MetalLB (poll until deployment exists, then kubectl wait)
- Timeout: 180s. If timeout reached, check if the Helm Application itself has issues
- If root-app has ComparisonError AND the controller deployment doesn't exist, apply the Helm chart directly using `helm template` + `kubectl apply` as a fallback. However, this is complex -- a simpler fallback is to ensure the Application is applied directly (`kubectl apply -f bootstrap/infra-envoy-gateway.yaml`) and let ArgoCD handle the Helm source separately. The root-app ComparisonError only affects Git-sourced Applications, not OCI-sourced ones. So the controller Application should still sync even when root-app has a ComparisonError. The fallback path should:
  1. Apply `kubectl apply -f bootstrap/infra-envoy-gateway.yaml` directly (ensures the Application resource exists even if root-app can't discover it)
  2. Wait for ArgoCD to sync the Helm chart (ArgoCD should be able to pull from docker.io/envoyproxy regardless of root-app status)
  3. kubectl wait for the Envoy Gateway controller deployment

```bash
# Step 12: Deploy Envoy Gateway controller
log_step "Waiting for Envoy Gateway controller..."
EG_WAIT=0
EG_TIMEOUT=180
until kubectl get deployment envoy-gateway -n envoy-gateway-system >/dev/null 2>&1; do
  if [ ${EG_WAIT} -ge ${EG_TIMEOUT} ]; then
    log_warn "Envoy Gateway not synced by ArgoCD -- applying Application directly"
    run_cmd kubectl apply -f "${BOOTSTRAP_DIR}/infra-envoy-gateway.yaml"
    # Wait for ArgoCD to process the Helm source
    sleep 30
    if ! kubectl get deployment envoy-gateway -n envoy-gateway-system >/dev/null 2>&1; then
      log_error "Envoy Gateway controller deployment not created after direct Application apply"
      exit 1
    fi
    break
  fi
  sleep 5
  EG_WAIT=$((EG_WAIT + 5))
done
run_cmd kubectl wait --for=condition=available deployment/envoy-gateway \
  -n envoy-gateway-system --timeout=120s
log_info "Envoy Gateway controller is ready"
```

**Step 13: Deploy Envoy Gateway configuration**
This step handles the kustomize-source Application (infra-envoy-gateway-config). This IS affected by the placeholder repoURL -- use the same direct-apply fallback pattern as MetalLB.

```bash
# Step 13: Apply Gateway API configuration
# The config Application uses the placeholder repoURL, so it cannot sync via ArgoCD.
# Apply the config manifests directly (same pattern as MetalLB fallback).

log_step "Applying Gateway API configuration..."
run_cmd kubectl apply -f "${BOOTSTRAP_DIR}/infra-envoy-gateway-config.yaml"
run_cmd kubectl apply --server-side --force-conflicts -f <(kubectl kustomize "${EG_CONFIG_DIR}")
log_info "Gateway API configuration applied"

# Wait for Gateway to be programmed (Envoy Gateway creates the DaemonSet after Gateway is applied)
log_step "Waiting for Envoy proxy DaemonSet..."
EGP_WAIT=0
EGP_TIMEOUT=120
until kubectl get daemonset -n envoy-gateway-system -l gateway.envoyproxy.io/owning-gateway-name=eg >/dev/null 2>&1; do
  if [ ${EGP_WAIT} -ge ${EGP_TIMEOUT} ]; then
    log_error "Envoy proxy DaemonSet not created after ${EGP_TIMEOUT}s"
    exit 1
  fi
  sleep 5
  EGP_WAIT=$((EGP_WAIT + 5))
done
run_cmd kubectl rollout status daemonset -n envoy-gateway-system \
  -l gateway.envoyproxy.io/owning-gateway-name=eg --timeout=120s
log_info "Envoy proxy DaemonSet is ready"
```
